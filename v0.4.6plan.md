## v0.4.6 should be a **performance-hardening** release

My reading is that the codebase is now modular enough to support a focused optimisation build. The public README shows a fairly clean split between the numerical kernel (`baselineAPI.py`, `preprocessing.py`), orchestration layers (`batch.py`, `mapping/_preprocess.py`, `single_fit/*`), and RamanSPy integration (`integration/*`), with an existing benchmark harness and regression suite already in place. ([GitHub][1])

The roadmap also makes the intended scope quite explicit: **v0.4.6 = Performance**, specifically reducing cube↔RamanSPy conversion overhead, improving memory efficiency, and profiling native versus RamanSPy preprocessing on representative workloads, while leaving broader API cleanup/deprecation work to **v0.4.7**. The same roadmap also says advanced features remain deferred until backend behaviour is mature. ([GitHub][1])

There is one important release-management issue: in the **public** snapshot I could inspect, the `CHANGELOG` currently goes up to **v0.4.4**, even though the README roadmap already includes **v0.4.5** and **v0.4.6**. So for v0.4.6, I would treat “record v0.4.5 cleanly” as part of the build gate, otherwise your release history becomes harder to audit. ([GitHub][2])

## What the current structure suggests

Two code-level points stand out.

First, mapping preprocessing already has a sensible cache at the execution layer: `_MappingPreprocessMixin` stores `_preprocessed_cube_cache` and `_preprocessed_x_cache`, so repeated full-map preprocessing is not the first place I would expect the main speed loss. That pushes attention downwards, into the baseline kernels and backend conversion path. ([GitHub][3])

Second, the native asymmetric baselines are a very plausible hotspot. In `baselineAPI.py`, `asLS`, `arPLS`, and `airPLS` all build sparse weighted systems and solve them with `spsolve`; `asLS` and `arPLS` form `D`, `W`, and `Z = W + \lambda D^T D` during iterative reweighting, while `airPLS` already improves this slightly by computing `DtD` once per call but still rebuilds `W`/`Z` and solves every iteration. That is exactly where I would concentrate v0.4.6 profiling first. ([GitHub][4])

A third structural observation: the batch layer still instantiates a fresh fitter for each spectrum, so the correct optimisation strategy is not to special-case `RamanBatch`, but to accelerate the shared preprocessing and backend machinery below it. That way single-spectrum, mapping, and batch all benefit from the same work. ([GitHub][5])

## Recommended build definition for v0.4.6

**Title:** Performance profiling and backend-path optimisation
**One-line objective:** Make preprocessing materially faster and lighter without changing scientific outputs or user-facing API behaviour. ([GitHub][1])

## Scope boundary

For this build, I would keep these **out of scope**:

* new preprocessing algorithms
* PL backend expansion
* user-facing API redesign
* deprecation removal / schema finalisation
* machine-learning features

That is because the roadmap already reserves API/deprecation cleanup for **v0.4.7**, and explicitly frames **v0.4.6** as a performance release. ([GitHub][1])

## Practical release target

A good definition of done for v0.4.6 would be:

1. benchmark harness upgraded from smoke-level evidence to representative evidence,
2. native asymmetric baselines measurably faster,
3. RamanSPy conversion path lighter on memory,
4. parity/regression tests all green,
5. no change to scientific behaviour or public API,
6. changelog/readme fully aligned. ([GitHub][1])

The next useful step is to turn this into a **file-by-file checklist with proposed test names and probable function-level edits**.
